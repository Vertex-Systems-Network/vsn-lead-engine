# Native Next sign-in and cancellation-error recovery

Native `/account/sign-in` now renders the username/password form and generic invalid/limited notices. The browser explicitly visits Django `/accounts/start-sign-in/` to seed its CSRF cookie and receive a fixed 303 return to Next. An exact stateless `/api/v1/account/sign-in-form/` GET requires that existing bounded cookie and returns only a masked token. Next forwards CSRF only on this anonymous context; session forwarding remains mandatory elsewhere, and authenticated contexts retain existing policy. No password or username is passed through Next, feedback storage, return URLs or error payloads.

The form posts directly to the existing protected Django login handler with a fixed native marker. Existing account/IP counters and connection-address authority remain unchanged. CSRF and Origin checks run before budgets/authentication. A rejected native login returns 303 to a fixed generic notice; a limited native login returns 303 with Retry-After 900 and never checks credentials. Existing standalone login retains its 200/429 behavior. Successful native login ignores supplied `next` and returns to configured LOGIN_REDIRECT_URL, with Django's session/CSRF rotation. Bootstrap/context do not authenticate or bypass attempt caps; notices are cosmetic and grant no authority. Without configured frontend origin, bootstrap falls back to the standalone Django login form.

Cancellation POST failures now return fixed invalid/changed/unavailable notice codes to the native job cancellation route when frontend configuration is enabled. Notice mode reads the existing authorized job snapshot, displays current status/revision and links to job review. It does not fetch form context, mint or preserve confirmation, auto-retry or cancel. Stale or expired confirmation requires explicit fresh review. Spoofed notices only select presentation; service authorization/state/revision/usage controls remain authoritative. Running/terminal jobs stay protected. With no frontend configuration, the existing escaped Django error form/statuses remain available; successful release-once/replay behavior is unchanged.

Engineering review: no migrations/dependencies, new data store, Next write proxy, payment/provider/scheduler activation or production collector change. Exact anonymous path/cookie forwarding is separate from authenticated transport. Fixed error codes eliminate any need for cancellation or login handoff storage. Server components, semantic labels/password autocomplete, escaped names, generic alerts and explicit recovery links were reviewed against the React checklist. Browser focus/responsive/WCAG/customer, shared-origin TLS/proxy/cookies, recovery/signup and production abuse/retention acceptance remain separate.

Verification: 162 Django cases (146 local passes/16 explicit PostgreSQL-only skips), five native-account tests and three cancellation-error tests; nine transport tests; Next lint/format/build/type; real Django/Next HTTP cookie bootstrap, wrong Origin, generic credential rejection, budget exhaustion, successful fixed return/CSRF rotation, stale cancellation snapshot with no form/token, explicit fresh confirmation/release-once and logout/old-session denial. Root 376 passed/1 skipped/28 subtests, ANPOS/Ruff/migration drift pass. Exact-head required checks, PostgreSQL migrations/settings/concurrency and Web CI remain merge gates. HTTP/SQLite is not browser or row-lock certification.
