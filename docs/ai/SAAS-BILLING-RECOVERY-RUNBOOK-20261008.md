# Internal billing diagnostics and recovery boundary

Use the local trusted deployment/operator execution context only. There is no HTTP diagnostics endpoint, webhook ingress, service credential, payment account or scheduler. The database/user arguments are context selectors, not remote authentication. Never expose the command as a remotely callable arbitrary-actor tool. Current active-user and owner/admin membership are rechecked under database locks; foreign/revoked contexts are denied.

Run `python apps/saas/manage.py billing_status --actor <current-admin-uuid> --workspace <workspace-uuid>` with the usual trusted SaaS settings. The command performs read-only, workspace-serialized diagnostics and creates no bindings, grants, counters, receipts or repairs. Output contains only switch/binding/grant status, revision/counts, entitlement deadline, accounting counters and generic mismatch codes. It omits actor/workspace/binding IDs, issuer names, event references, body hashes, signatures, key IDs, secrets and payment details. Even aggregates may be confidential; keep operator output in authorized internal channels.

`ledger_order_mismatch` means binding revision/issuance or count differs from persisted contiguous history. `binding_history_mismatch` means an existing binding was moved across recorded tenant/issuer coordinates. `entitlement_binding_mismatch` means the grant points outside the current local binding. `entitlement_snapshot_mismatch` means active/deadline differs from the latest recorded snapshot. These observations do not certify complete ledger authenticity, provider payment truth or legal retention; the report deliberately does not scan/reverify old signed bodies or infer source rights.

On any mismatch, leave live activation disabled and preserve ledger/counters/periods/reservations. Investigate the trusted adapter's original evidence in its separately authorized system; do not dump it into logs, a public issue or this repository. Do not edit revision numbers, replay an old grant as a repair, refund pending work or delete evidence. A repair requires a reviewed preservation/compatibility plan and exact trusted provider/account mapping; there is no automated repair command.

For a contiguous event gap, obtain the missing trusted event or use a separately reviewed reconciliation protocol. Never increment local revisions to bypass ordering. For an exact replay, present the same bytes while current key/binding/freshness still permits verification; denied old/revoked evidence cannot restore an earlier entitlement. Unknown provider effects keep reserved capacity. Confirmed past effect settlement and existing safe cancellation/expiry paths retain their respective authority.

Default-disabled switches, empty signing registries and fixture keys are not production provisioning instructions. Before enabling actual billing, verify provider payment sandbox/signature/account mapping, authenticated ingress/recovery, commercial/legal rights, log redaction, pseudonymous event/fingerprint/actor retention, encryption/backups, migration preservation and qualified privacy review. No automatic ledger deletion, backup/WAL purge, payment refund or external account change is authorized by this runbook.
